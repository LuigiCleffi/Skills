# Living Documentation

Executable specifications are the source of truth for what the system does; living documentation is the report built from them that states each requirement, its examples, and whether the current build satisfies them. Organize and report it around features and requirements, not around test pass/fail counts, and include requirements that have no automated criteria yet so progress is not overstated.

## What makes documentation "living"

- It is generated by the build from the same feature files and step results that verify the system, so it cannot drift from the code.
- It answers three audiences at once: stakeholders ("does it do what I need?"), analysts and testers ("does it do what we agreed?"), developers ("does it work, and how?").
- It closes the loop with discovery: the examples people discussed appear verbatim in the report, which is a strong reason for stakeholders to keep participating.
- Testers use it to see what is already covered and where to aim exploratory testing; new team members and support teams use it to learn what the system does and how.

If nobody outside the development team ever opens the report, it is not yet living documentation; it is a test log.

## Feature readiness

A feature is ready when every one of its acceptance criteria passes. Report at feature (or story) level first, with drill-down to scenarios and steps.

| Feature | Criteria | Passing | Pending | Failing | Ready |
|---|---|---|---|---|---|
| Submit leave request | 5 | 5 | 0 | 0 | yes |
| Manager approval | 4 | 2 | 1 | 1 | no |

- Distinguish failing (implemented, broken) from pending (specified, not yet automated or implemented). Mixing them hides real regressions.
- Keep the readiness rule strict: one failing criterion means not ready. If a criterion turns out not to matter, delete it rather than tolerate it red.

## Feature coverage, not just test results

Test results only know about requirements that have tests. Feature coverage also counts requirements that exist in the backlog but have no automated criteria.

- Example: all scenarios for "Authentication" are green, but only one of its three stories has scenarios. Readiness looks 100%; coverage is about 33%.
- Feature coverage is not code coverage. Code coverage says which lines ran; feature coverage says which agreed behaviors are specified and verified.
- Coverage is only as complete as the requirements the tool knows about. Agile backlogs stay coarse beyond the next iteration, so treat future epics without stories as "not started", not as "no requirements".
- To compute it, the reporting step needs a requirements source beyond the test output: a directory hierarchy of feature files, or the product backlog.

## Linking to the product backlog

Store the story narrative in the backlog tool and the acceptance criteria in feature files; join them with a tag carrying the issue key.

```gherkin
@issue:LEAVE-42 @capability:time-off
Feature: Manager approval of leave requests
  Managers approve or decline requests from their direct reports.
  Policy reference: HR handbook section 4.2 (carry-over limits).

  Rule: Only the direct manager can decide
    @security
    Scenario: A peer cannot approve a colleague's request
      Given Ana has a pending request for 3 days
      When her teammate Rui tries to approve it
      Then the request should remain pending
      And Rui should see "Only Ana's manager can approve this request"
```

- Minimum integration: the report links each feature to its backlog item. Better: the report pulls the narrative and epic hierarchy from the backlog, so nothing is written twice.
- Some teams push results back, flagging a card when its criteria fail. Decide this deliberately; noisy automated status changes erode trust in the board.
- Pick one tag convention (`@issue:KEY` or `@KEY-123`) and enforce it in review or with a lint step; inconsistent keys break the join silently.

Current note: Thucydides is now Serenity BDD, which supports issue tags and Jira integration and can build requirement hierarchies from feature directories. For Cucumber, common options are the built-in HTML formatter, Cucumber Reports (masterthought) over JSON output, and Allure. SpecFlow has been discontinued; Reqnroll is its community successor for .NET.

## Organizing the documentation

Offer more than one view; each serves a different reader.

- **Requirements hierarchy** (capability > feature > story > scenario): best for "what does the system do and how". Mirror it in directories so the tool can derive it without a backlog:

  ```
  features/
    time_off/
      submitting_requests/submit_leave_request.feature
      approvals/manager_approval.feature
    payroll/...
  ```

- **Cross-cutting tags**: nonfunctional concerns (`@security`, `@performance`, `@accessibility`) and integrations (`@payroll-api`) spread across many features. Prefer a reporting tool that filters an existing run by tag over rerunning the suite per tag.
- **Release or iteration**: tag (`@release-2.3`) or, better, read release assignment from the backlog so it is managed in one place. A release view shows only what is planned, its readiness and its unfinished criteria, and is a direct input to release notes.

Keep the tag taxonomy small and documented (a `features/TAGS.md` or the README): kind (`@security`), ownership, release, issue key, and execution control (`@wip`, `@slow`). Ad-hoc tags multiply until filtering means nothing.

## Enough prose to be documentation

- User stories are placeholders for conversations; once criteria are agreed, add the context a reader needs: why the rule exists, regulatory references, links to detailed business rules.
- Put that context in the feature description (free text under `Feature:`) or in `Rule:` descriptions, or in the backlog item if the report pulls it in. Do not bury it in step definition comments nobody sees.
- Wiki- or page-driven tools (FitNesse, Concordion) give total freedom over layout, at the price of hand-maintained page structure and weak aggregate reporting. Use them only when tabular, analyst-authored specs are a firm requirement.

## Technical living documentation

Unit and integration specs are the documentation for developers; readability matters more than report polish.

- Name contexts and behaviors so the IDE or `--verbose` runner output reads like an outline (see the unit-testing skill).
- Organize test directories by functional slice rather than strictly mirroring production packages; behavior survives class renames and splits, and a mirrored structure ties tests to implementation.
- A test that needs protected or private members is coupled to implementation; specify through the public API.
- Complement specs with a short architecture note (decision records, a diagram) rather than duplicating what specs already show.

## Legacy systems

- Start with high-level acceptance scenarios that record how the system behaves today (characterization), focused on the riskiest, most frequently changed areas. They document and guard against regressions at once.
- Retrofitted unit tests tend to be shallow because the original intent is lost; write them where you are about to change code, in the spirit of documenting current behavior and showing how each class is used.
- When a characterization scenario reveals behavior that looks wrong, record it as is, tag it (for example `@questioned`), and raise it with the product owner instead of "fixing" the scenario silently.

## Workflow

1. Identify the readers and the questions each needs answered (readiness, coverage, release scope, how-it-works).
2. Choose a requirements source: directory hierarchy, backlog integration, or both; define the issue-tag convention.
3. Configure the BDD runner to emit machine-readable results (Cucumber JSON or messages, Serenity output) on every build.
4. Generate a feature-level report with drill-down; verify it separates passing, failing and pending, and shows requirements with no scenarios.
5. Add a tag taxonomy for cross-cutting concerns and releases; document it next to the feature files.
6. Publish the report where non-developers can reach it (see the build-process skill) and review it in the iteration demo.
7. Keep feature descriptions and unit spec names current during refactoring; treat unreadable reports as defects.

## Red flags

- Reports that list only test counts and stack traces, with no feature or requirement view.
- "All green" presented as done while stories in the epic have no scenarios at all.
- Code coverage percentage used as a progress or readiness metric.
- Story narratives copied into feature files and the backlog, then edited in only one place.
- Pending and failing scenarios shown in the same color or count.
- Tags invented per developer, with no documented meaning.
- Living documentation regenerated by hand before demos instead of on every build.
- Characterization scenarios edited to match what the team wishes the legacy system did.
- Test packages mirroring production classes one to one, breaking on every refactor.
